## 4. Zasady prowadzenia (obowiązują każdego agenta i mnie)

1. Worktree tworzy CTO z `origin/staging` (`~/Developer/wt/<nazwa>`, `node_modules` symlink); pierwsza komenda agenta = `git rev-parse HEAD`.
2. Baza robocza = kopia `consultify_staging_czysta` w kontenerze `consultify-pg18` (port 54418), własne porty, kasowana po pracy. Żywe bazy staging/demo: tylko odczyt, chyba że zlecenie mówi inaczej — wtedy zrzut + manifest przed.
3. Meldunek: STANOWISKO · POMIAR PRZED→PO · CO ZMIENIŁEM · DOWÓD (plik:linia, zrzut, HTTP) · SHA per etap · STOP-y. Commit po każdym etapie. Bez pusha.
4. Scalenia, push, deploy, promocja, zmienne Railway, rejestr, Codex — wyłącznie CTO. Zmienne Railway ZAWSZE z `--skip-deploys`, po nich odczyt health i porównanie SHA (nie „ok").
5. Codex dostaje tylko duże bloki mechaniki tylnej z markerem SHA i materiałami w repo; odbiór 3-warstwowy (Opus kod → Sonnet runtime → podpis CTO); FIX-y po Codexie wewnętrznie.
6. Właściciel nigdy pierwszym testerem wizualnym; nic nowego wizualnie bez prototypu; jeden żywy obraz, Tak/Nie.
7. Punkt cofnięcia przed każdą operacją (tag, zrzut, manifest). Produkcja nietykalna.
