# Przegląd bezpieczników — 2026-09-01

Pytanie zadane każdemu bezpiecznikowi, w PEŁNEJ (rozszerzonej) wersji:

1. **Co robi, gdy NIE MOŻE wykonać pomiaru** (brak esbuild, brak pliku wejściowego, plik się nie parsuje, zależność niedostępna)?
2. **Co robi, gdy NIKT GO O POMIAR NIE POPROSIŁ** (pusta lista wejściowa, opcjonalny parametr nie podany, staging pusty, filtr nie dopasował nic)?

Zasada: **brak pomiaru nie jest wynikiem pozytywnym**, i **cisza domyślna jest też zachowaniem bezpiecznika**.

Metoda: dla każdego pliku — przeczytanie kodu (nie tylko nazwy/komentarza), próba realnej mutacji tam gdzie to bezpieczne, dowód `EXIT=` przed/po. `dev-render/main.tsx` (plik współdzielony) mutowany z kopią zapasową poza repo, przywrócony natychmiast po pomiarze — `git diff` puste na koniec (zweryfikowane wielokrotnie).

### Skutek uboczny warty odnotowania

`scripts/check-dev-render-parytet.mjs` zawiera **literalny bajt NUL** (`\x00`) jako separator klucza mapy w stringu `` `${a}\x00${b}` `` (linia ok. 8823 w bajtach pliku) — legalny, celowy kod JS. Ale to sprawia, że `file` widzi plik jako "binary data", a **zwykły `grep` (bez `-a`) po prostu nie dopasowuje niczego w tekście PO tym bajcie** — bez ostrzeżenia, bez błędu, pusty wynik. Złapane przypadkiem podczas audytu (szukałem `process.exit` przez grep, dostałem pustkę, plik miał `process.exit(0)`/`process.exit(1)` dobrze widoczne przez `Read`). To jest DOKŁADNIE ten sam kształt co pułapka `grep --include` w zsh z pamięci projektu — pusty wynik grep nie jest dowodem braku wystąpień. Każdy PRZYSZŁY bezpiecznik grepujący ten konkretny plik powinien używać `grep -a` albo narzędzia tekstowego świadomego kodowania (python/node), nie gołego `grep`.
