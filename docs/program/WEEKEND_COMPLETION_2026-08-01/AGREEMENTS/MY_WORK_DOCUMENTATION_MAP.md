# My Work — mapa pakietów dokumentacji

## 1. Decyzja

My Work pozostaje jedną pozycją głównego menu i jednym osobistym centrum pracy,
ale jego funkcje otrzymują osobne kontrakty produktowe. Jeden dokument modułu
nie jest wystarczający do opisania ich różnych celów, danych, AI i golden flows.

My Work agreguje i orkiestruje. Nie przejmuje prawdy obiektów należących do
Initiatives, Execution, Results, Finance, Interview, Assessment, Tools ani
Materials.

## 3. Pakiet nadrzędny My Work

Dokument nadrzędny opisuje wyłącznie:

- rolę My Work jako osobistego cockpit/orchestratora;
- wspólny shell i nawigację;
- identity, role, ACL i scope projektu/organizacji;
- projection/read-back zamiast kopiowania prawdy;
- wspólne deep links, search, command row i prawy panel Teresy;
- wspólne statusy loading/empty/degraded/error/permission;
- notification, audit i cross-module handoff;
- spójność mobilną i accessibility;
- zbiorczy golden flow dnia pracy.

Nie powtarza pełnych funkcji poszczególnych pakietów.

## 4. Wspólne invariants

Każdy pakiet:

- wskazuje właściciela każdego obiektu;
- zachowuje source ID, provenance i deep link;
- nie ogłasza sukcesu przed read-backiem właściciela;
- pokazuje, czy obiekt jest lokalny, projekcją czy proposalem;
- rozdziela sugestię AI, akceptację człowieka i wykonany zapis;
- definiuje role Teresy, zakazane działania i standard jakości;
- ma pełny katalog funkcji, lifecycle, dane, uprawnienia i integracje;
- ma golden flows, stany błędów i Definition of Done;
- używa wspólnych kanonów UI 2026 i artefaktów aplikacji.

## 6. Bramka kompletności My Work

My Work jest dokumentacyjnie zamknięty dopiero, gdy:

- wszystkie siedem pakietów jest zaakceptowanych;
- nie ma sprzecznych właścicieli Tasks, Decisions, documents ani initiatives;
- każdy cross-module write ma proposal/confirmation/read-back;
- wszystkie role i visibility są spójne z Organization/Projects;
- pakiety tworzą jeden zrozumiały dzienny przepływ użytkownika;
- zbiorcze testy obejmują nawigację i przejścia między pakietami.
