## R1 — INWENTARZ (rdzeń)

Tabela: preferencja · komponent · gdzie w interfejsie · gdzie zapisywana · czy przeżywa zimne
logowanie · czy ma test · **czy użytkownik to w ogóle znajdzie**. Cztery warstwy sprawdzone
osobno: kod, wołacz, montaż, widoczność. Znalezienie wołania API nie dowodzi, że komponent
jest renderowany.

Commit po `R1`.

## R2 — ODZYSKANIE ZAKRESU (rdzeń)

Przeszukanie korpusu uwag właściciela po tym, co naprawdę zgłosił. Jeżeli po tym zakres nadal
jest nieokreślony — kończysz STOP-pytaniem sformułowanym tak, żeby dało się odpowiedzieć jednym
zdaniem, i **to jest pełnowartościowy wynik dyżuru**. Budowanie na domyśle nie jest.

Commit po `R2`.

## R3 — PROTOTYP ZA FLAGĄ OFF (rdzeń)

Tylko to, czego zmierzalnie brakuje, i tylko w istniejącym miejscu ustawień. Drugi ekran obok
istniejącego to ten sam dług, który program mierzy jako rozjazd. Flaga OFF także przy braku
zmiennej środowiskowej — osobny przypadek testowy.

Commit po `R3`.

## R4 — DOWÓD TRWAŁOŚCI (rdzeń)

Realna baza na własnym kontenerze. Zapis, wylogowanie, zimny odczyt **osobnym** klientem — nie
tym, który pisał. Atrapa bazy zwraca sukces dla każdego zapisu niezależnie od warunku, więc
zielony test na atrapie nie jest dowodem. Migracja addytywna sprawdzona łańcuchem od zera
w trybie strict na pustej bazie.

Commit po `R4`.

## R5 — KADRY I LISTA CZEKOWANIA (rdzeń)

Cztery kadry: jasny i ciemny, polski i angielski, kanonicznym narzędziem. Każdy obejrzany przez
`Read` i opisany z nazwy. Lista czekowania część B w zakresie dotyczącym powierzchni ustawień,
z „n/d + powód” tam, gdzie nie dotyczy.

Commit po `R5`.

## R6 — RAPORT

Ile z B6 już istniało. Co dołożono. STOP-pytania. TWIERDZENIA NIEZWERYFIKOWANE.

## Prawo zatrzymania

„Inwentarz gotowy, zakres B6 nieodzyskiwalny z korpusu, oto jedno pytanie do właściciela”
jest lepszym wynikiem niż nowa powierzchnia zbudowana na domyśle. Funkcja, która duplikuje
istniejącą, kosztuje dwa razy: raz przy budowie, raz przy usuwaniu.
