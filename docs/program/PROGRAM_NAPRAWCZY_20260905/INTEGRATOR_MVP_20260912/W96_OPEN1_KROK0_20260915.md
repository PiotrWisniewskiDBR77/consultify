# OPEN-1 — KROK 0: pomiar siedmiu list „podgląd bez wejścia”

**Werdykt: STOP przed kodem produkcyjnym.** Pomiar na bazie `9cf10528e3` potwierdza siedem niespójnych wejść. Cztery mogą użyć istniejącego ekranu docelowego po doprowadzeniu identyfikatora i jawnej akcji. Trzy wymagają najpierw decyzji o kanonicznej powłoce albo kontrakcie danych. Ta paczka nie zmienia kodu produktu, tras, flag, migracji ani danych.

## Zakres i metoda

Źródłem zakresu są Wpis 96 oraz uwagi właściciela U-22, U-27, U-28, U-32, U-36, U-38 i U-39. Dla każdej listy sprawdzono:

1. zachowanie pojedynczego kliknięcia i akcji z kebaba/podglądu;
2. trasę, flagę i handler;
3. istnienie pełnego ekranu obiektu;
4. najmniejszą uczciwą zmianę, która nie tworzy równoległego ekranu.

## Podział na wdrożenie

### OPEN-1A — przewody do ekranów istniejących

1. Assessment Session record → istniejący `AssessmentSessionEditorView`.
2. Audits Sessions → istniejący browser/workspace kryteriów.
3. Audits candidate → widoczne Register, a po rejestracji kanoniczna karta Inicjatywy.
4. Execution Decisions → kanoniczna karta decyzji po `decision.id`; relacja do inicjatywy pozostaje relacją.

Warunek wejścia: test matrycy kliknięć dla row click, kebab i preview; brak toastów zastępujących nawigację; deep-link po odświeżeniu nadal otwiera ten sam obiekt.

### OPEN-1B — powłoki wymagające decyzji

1. Audit pack object: zaakceptowana anatomia i granica edycji draft/published.
2. Project Object Page: osobny projekt z `analiza-projekty-20260915`; plik `MyProjects.tsx` pozostaje nietknięty do decyzji.
3. Task Object Page dla `/api/tasks`: wspólny kontrakt uprawnień dla właściciela, managera i administratora; preview nie może udawać pełnego Open.

### OPEN-1C — higiena listy decyzji

Techniczne rekordy Tools pozostają trwałym śladem. Filtr UI opiera się na `decisionType`, nie na tekście tytułu. Ich właściwym miejscem jest historia/workflow sesji Tools. Filtr nie może ukryć zwykłej decyzji powiązanej z narzędziem tylko dlatego, że tytuł zawiera słowo „tool”.

## Kolejność rekomendowana

1. OPEN-1A dla Assessment, Audits Sessions i Audits candidate — małe przewody do istniejących ekranów.
2. OPEN-1C + karta Decision — usuwa martwe wpisy z listy i naprawia semantykę kliknięcia.
3. Osobna akceptacja makiet Audit pack, Project i Task Object Page.
4. OPEN-1B dopiero po decyzjach. Każda powłoka jako osobna paczka, za flagą domyślnie OFF, z EN light+dark i pełną matrycą wejść.

## Granica STOP

Nie dodano żadnego handlera, route, ekranu, flagi, migracji, tłumaczenia ani testu produktu. Nie uruchamiano aplikacji ani nie zapisywano danych. Następny krok wymaga rozdzielenia OPEN-1A/1B/1C przez CTO, ponieważ trzy brakujące powłoki mają różne modele uprawnień i nie powinny zostać złączone w jeden duży ekran.
