## 1. Status model

| Status             | Meaning                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| **RUNTIME PASS**   | Performed manually in the deployed canonical editor, read back from UI and reopened when durability matters. |
| **CONTRACT PASS**  | Real implementation and focused automated proof exist, but the final deployed UI action was not repeated.    |
| **PENDING DEPLOY** | Implemented and tested after the last accepted runtime deployment. It is not yet runtime proof.              |
| **PARTIAL**        | Useful narrower workflow works; expected professional breadth or final artifact proof is missing.            |
| **GAP**            | No honest manual path exists in the canonical editor.                                                        |
| **UNPROVEN**       | Capability may exist, but the required failure, concurrency or destructive scenario was not triggered.       |

When an older row in a source audit conflicts with its later “final verification” section, the later dated/deployed evidence wins. “Control present” alone is never promoted to runtime PASS.

## 7. Intuitiveness and visual acceptance

A capability is “intuitive” only when all applicable checks pass:

1. **Recognition:** the verb and Lucide icon match the shared registry (`Plus`, `Copy`, `Pencil`, `Trash2`, `GripVertical`, `Undo2`, `Redo2`, `MessageSquare`, `History`, `Download`, `Share2`). No emoji, private SVG family or format-logo toolbar controls.
2. **Placement:** lifecycle/top actions are in the top row; sections/sheets/slides in the left rail; selection/content/appearance/data/accessibility in the right inspector; the center canvas remains dominant.
3. **Discoverability:** a first-time user can locate the command without Teresa, browser-native prompts or undocumented glyphs. Rare actions belong in overflow, not duplicated across surfaces.
4. **Feedback:** mutation shows saving/saved/error; destructive actions name the target and require an application-owned confirmation; long operations show named progress.
5. **Durability:** save, cold reopen and native export preserve semantic content, formulas, styles, source links and identity. A visually successful but non-persistent action fails.
6. **Reversibility:** undo/redo works for session mutations; structural restore creates or identifies a recoverable checkpoint.
7. **Accessibility:** every action has an accessible name, visible focus, keyboard reachability and WCAG AA contrast; icon-only targets are at least 36×36 px with tooltip.
8. **Visual consistency:** neutral-first chrome, token colors, one focus blue, no operational gradients, `rounded-xl` elevated menus/modals and no obsolete raster illustration.
9. **Truthfulness:** template thumbnails match generated output; download labels state exact format; unsupported breadth is described rather than simulated.
10. **Manual parity:** every AI-generated element can be selected, edited, reordered, duplicated, deleted, sourced where relevant and undone manually.

## 8. Release acceptance gates

### Suite-wide gate

The Materials suite is accepted for manual work only when:

- zero dead, duplicated, clipped or inaccessible primary controls exist in the three canonical editors;
- create/open/rename/save/cold-reopen, structural CRUD, undo/redo, QA and native export pass for each applicable tool;
- at least one non-trivial artifact per tool survives cold reopen and native-format validation;
- export gates cannot be bypassed accidentally and failures preserve authored input;
- light/dark and 1280/1440 screenshots pass for shell, menu, modal, empty/loading/error and open inspector;
- no runtime P0/P1 defect is hidden behind a contract-only test.

### Tool-specific completion gates

| Tool       | Minimum accepted artifact                                                                                                                | Additional gate                                                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Word       | Multi-section report with headings/lists, table or KPI/risk object, source/assumption, comment, image with alt, checkpoint and DOCX/PDF. | Deploy and smoke `c166150e43` + `4fc908ffb5`: collapse, image upload→replace→reload, actual image in DOCX/PDF, QA highlight.          |

## 9. Consolidated residual backlog

### P1 — blocks full professional parity

1. Word: deploy/runtime proof for collapse timing, visible QA highlight and real image upload/replace/alt embedded in DOCX/PDF.
2. Excel: deploy/runtime proof for import, manual chart, conditional formatting, hide/unhide, merge/unmerge and reconnect queue; native XLSX artifact capture.
3. Cross-tool: deterministic two-session conflict and forced offline/retry proof.

### P2 — breadth and polish

1. Word: indentation, custom paragraph spacing, font-family browser, quote/chart authoring, image crop model, selection-anchored comments and shortcut reference.
2. Excel: broader Excel-compatible formula engine, clearer diagnostics and uniform blank-workbook/save-as/share flows.
3. PowerPoint: arbitrary named-master picker, crop/focal/mask controls, richer per-run typography, destructive restore runtime proof, and optional visual 16:9 PDF parity.
4. Visual: replace remaining legacy assets using the migration rule; keep all three editors on one shell/icon/menu grammar.

## 10. Verdict

- **PowerPoint:** strongest end-to-end manual workflow; accepted `PASS_WITH_P2`, no known P0/P1 authoring failure.
- **Word:** core workflow is operational and well governed; pending deployment smoke prevents declaring the newest image/collapse work runtime-complete.
- **Excel:** durable spreadsheet editing is now materially broader than the initial audit, but the newest advanced operations and native XLSX artifact still need runtime closure.
- **Suite:** suitable for serious manual correction and authoring, but not yet a single unconditional “full desktop-suite parity” claim. Release messaging must use the per-tool statuses and residuals above.
