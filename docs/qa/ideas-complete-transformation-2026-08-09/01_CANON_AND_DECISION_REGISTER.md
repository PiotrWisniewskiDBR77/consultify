## Purpose

This document is the single lookup a future engineer or agent should consult **before** implementing or auditing anything in the Ideas transformation program, instead of re-reading the full standards tree each time. For every decision area named in doc 11 §2 it records: where the actual file lives in this worktree (or that it does not exist), the binding decision the file actually contains in plain language, and any contradiction found between that file and its supporting evidence or a neighboring row. It does not restate every rule — it tells you which document rules and what that document says, so you know which file to open for the full text before you change behavior in that area. Per doc 11 §2's conflict procedure, unresolved conflicts are flagged for the owner rather than silently resolved with an invented third variant; resolvable conflicts apply the stated hierarchy (`CANON.md` plus the newer Idea-owner decision) and say so explicitly.

## Decision register

### Idea model and Z1–Z4

- **Primary authority:** `docs/standards/idea-workspace/01_MODEL_I_ZASADY.md` — present, 106 lines.
- **Supporting evidence:** chapters 02–12 — chapters 02–12 all present except 13 (missing, see below); 14 does not exist at all.
- **Binding decision:** An Idea is **one data object** (one graph + metadata), viewed through four representations (Mind Map, Whiteboard, Process Flow, Table); switching representation is a local view preference, never a conversion, and never mutates data or another collaborator's screen. Four rules bind every later chapter: **Z1** identical action name/icon/place/shortcut/behavior across tools unless a documented exception exists; **Z2** surfaces must look like one system, not bolted-on technical panels; **Z3** zero placeholders — every action has a real handler, enforced mechanically via the action registry (chapter 02), not by promise; **Z4** every UI action must be callable by talking to Teresa, no exceptions. Every action has exactly one of ten declared scopes (`workspace`, `current_view`, `selected_items`, `single_item`, `edge`, `lane_frame`, `table_row`, `table_column`, `table_cell`, `external_artifact`) which determines where it is allowed to live; §3 states eight hard scope-placement prohibitions (e.g. a `workspace`-scope action never lives in the left rail; "Delete selected" never renders with nothing selected). §1 states explicitly this chapter wins in any conflict with later chapters.

### Conversion/import/export/templates

- **Primary authority:** chapter 10 (`10_KONWERSJA_EKSPORT_IMPORT_SZABLONY.md`) — present, 201+ lines.
- **Supporting evidence:** master program §§9–10 ("9. Conversion, lineage and downstream integration", "10. Data integrity, collaboration and reliability") — both present.
- **Binding decision:** Fixes six frequently-confused concepts into non-interchangeable definitions: representation switching (same graph, zero I/O, no new entity), representation generation (out of scope for this standard — deferred to decision D3 as a separate "semantic mapping" project, explicitly not something to slip into a repair phase), new Idea creation, conversion-to-artifact (reads the graph, creates a durable separate record in another module — Initiative/Task/Decision/Report/Presentation/Team Chat — plus a backlink; the Idea itself is not consumed and gets a conversion-history entry), file export (renders to a file outside the system; never creates a persistent Consultify record — a PDF report that *also* creates a Reports-module record is conversion, not export), import (brings external data in, may replace or append to the graph), and templates (applies an internal, pre-built structure). The deciding rule: if an operation does not produce a file and does not create a persistent record outside the Idea, it is neither Export nor Convert. Conversion scopes must be shown explicitly to the user and always require a preview before committing.

### Table

- **Primary authority:** `docs/ui-standards/03-modules/TABLE_AND_PREVIEW_CANON.md` (v1.1, `status: canonical`) and `docs/ui-standards/DOKTRYNA_TABELA_NIE_EXCEL.md` (dated 2026-07-13) — both present.
- **Supporting evidence:** "P15 runtime" — real term, found throughout chapters 05/06 of the Ideas standard and the master program/doc 11 (`P15TableToolbar`, `onPlatformUndo` vs legacy `nodesUndo`, "Table → P15 docelowy, legacy wygaszany"); P15 denotes the target platform-table engine that Ideas' Table representation is migrating onto.
- **Binding decision, and a genuine tension between the two authorities:** `TABLE_AND_PREVIEW_CANON.md` is the canon for `StandardTable`/`StandardModuleBar`/`StandardPreview` — fixed-schema **list** screens where each row is a record of one entity type and a click opens that record's preview (its own TL;DR: one table component `FilterableTable`, one card view `GridView`, one status-chip family, sticky left-aligned headers, right-aligned numbers, no row-hover height change, persisted column widths, a closed-by-default preview pane with a fixed footer button order). `DOKTRYNA_TABELA_NIE_EXCEL.md` exists specifically to stop that canon from being misapplied: it defines three distinct table-like entities — (1) LISTA = fixed-schema record list → `StandardTable`, (2) EXCEL = cells+formulas/model → an `.xlsx`-rendering artifact engine, not `StandardTable`, (3) PLATFORMA-TABEL/Matryca = user-defined dynamic schema with realtime collaboration → SPEC-A archetype D, explicitly naming `IdeaTableTool`/`GridView` as this third category and stating in its own "Decyzja 07-13" that these **stay** as platform-table and are **not** to be migrated onto `StandardTable`. **Conflict:** doc 11 §2 cites `TABLE_AND_PREVIEW_CANON.md` as a primary authority for "Table" without qualification, but DOKTRYNA (cited in the same row) explicitly excludes Ideas' own Table tool from that canon's component contract. Resolution applying CANON.md §2/§2.1's hierarchy: DOKTRYNA_TABELA_NIE_EXCEL.md is the more specific classifier for "which standard applies to which table-shaped screen" and is not superseded by TABLE_AND_PREVIEW_CANON.md, so **Ideas' Table representation is governed by the SPEC-A Matryca archetype (`ARTIFACT_ANATOMY_STANDARD.md` §13) and the P15 platform-table engine, not by the `StandardTable` component** — TABLE_AND_PREVIEW_CANON.md's *general* conventions (alignment, empty-cell dash, honest empty/loading/error states, status-chip family) may still apply by analogy where SPEC-A doesn't already specify something different, but its component-level contract (`FilterableTable`, `StandardModuleBar`) does not bind the Ideas Table tool.
