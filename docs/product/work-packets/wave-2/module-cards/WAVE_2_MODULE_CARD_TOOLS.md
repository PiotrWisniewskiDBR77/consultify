> Cluster: `Business Enablement`
> Scope: broad consulting tools product beyond the current V8 bridge

## 1. Module scope

This card covers the tools product as a whole:

- catalog,
- sessions,
- framework tools,
- AI-assisted consulting workflow,
- outputs,
- and integration with the rest of the platform.

## 3. Intended product behavior

`Tools` should be a real consulting workspace:

- discover tools clearly,
- start a session,
- use AI safely inside the session,
- finalize results,
- and promote outputs into initiatives, reports, presentations, and knowledge.

## 4. Current repo and doc truth

The current truth is bridge-heavy:

- V3 product contracts are strong,
- `TOOLS_V8_SSOT.md` is a V8 bridging contract,
- the gap analysis still marks the broad module as partial and pushed to `8.2`,
- so the system has strong obligations and runtime integration rules, but not yet one fully refreshed `Tools v8` product program.

## 5. Competitive standard

The benchmark is consulting and workflow systems where:

- the tool library is clear,
- sessions are structured,
- AI guidance is useful but governed,
- and outputs become durable downstream work.

## 6. Current-state assessment

- `User value`: partial. Strong consulting potential exists, but the product canon is split across V3 and V8 bridge docs.
- `Flow completeness`: partial. Library-session-output flow exists conceptually, not as one refreshed Wave 2 execution package.
- `UX quality`: partial. Strong standards exist, but full V8 user-facing coherence is still open.
- `Data / logic quality`: good. Session, traceability, and governance rules are explicit.
- `Integration quality`: good. Tools are already tied to context, retrieval, execution spine, and outputs.
- `Trust / governance`: good. Governance obligations are unusually explicit.
- `Market standard fit`: partial. Strong infrastructure and doctrine, incomplete product consolidation.

## 7. Main gaps

- no one full `Tools v8` product package beyond the bridge,
- no fresh execution-grade module plan for the whole tools family,
- split truth between V3 product canon and V8 platform obligations,
- missing clearer modern tool discovery and session UX target,
- missing unified Wave 2 packet chain.

## 8. Minimal acceptance state now

The first acceptable Wave 2 state is:

- one canonical `Tools` product package,
- one visible library-to-session-to-output user journey,
- and one explicit AI-governed runtime contract that a future implementation team can execute from.

## 9. Full 100% target state

`Tools` reaches 100% only when it provides:

- one coherent tool catalog,
- one session runtime pattern,
- one AI governance model visible to the user,
- one output/promotion model,
- and one durable bridge to knowledge, initiatives, reports, presentations, and assessments.

## 10. Top missing functions and flows

- catalog discovery and tool selection
- session start with context binding
- AI propose/accept workflow inside tool sessions
- finalization and promotion to downstream modules
- knowledge-bank use inside tool work without bypassing governance

## 11. Proposed bounded delivery packets

1. `Tools v8 product canon`
   - unify V3 product truth and V8 obligations into one execution package
2. `Canonical tool-session flow`
   - define the one preferred session journey
3. `AI-governed tool runtime`
   - make AI behavior visible, bounded, and testable
4. `Promotion and outputs closure`
   - finish the path from tool result to downstream artifact/work object

## 12. Risks and dependencies

- depends on `Assessment`, `Outputs`, `Knowledge`, and `Prompt OS`,
- risks staying a bridge forever instead of becoming a product,
- risks opening too many per-tool variations before the shared system is stabilized.
