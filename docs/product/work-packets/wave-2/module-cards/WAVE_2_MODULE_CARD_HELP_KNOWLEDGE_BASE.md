> Cluster: `Knowledge And Support Systems`
> Scope: full help and knowledge product beyond the carried bounded closeout

## 1. Module scope

This card covers:

- help center,
- transformation knowledge base,
- contextual support,
- Teresa-led discovery,
- editorial operations,
- and optional academy-adjacent enablement surfaces inside the module.

## 3. Intended product behavior

`Help / Knowledge Base` should become a Teresa-led transformation learning and support system:

- support help,
- specialist knowledge,
- contextual guidance,
- inspiration,
- and curated educational content

all under one governed knowledge product.

## 4. Current repo and doc truth

Current truth is strong on documentation:

- the package has benchmark, SSOT, IA, contextual integration, content ops, and backlog docs,
- Wave 1 ratified a bounded must-have closeout,
- but the package itself says the remaining work is implementation, content seeding, editorial setup, and recommendation logic,
- so product definition is strong while runtime breadth is still not fully delivered.

## 5. Competitive standard

This should be judged against:

- Atlassian, Intercom, and Zendesk for help structure,
- modern knowledge products for specialist content,
- and in-product guided-help systems for contextual support.

## 6. Current-state assessment

- `User value`: good. The product promise is clear and serious.
- `Flow completeness`: partial. Contextual help and support structure are documented strongly; delivery depth is still open.
- `UX quality`: partial. Help panel and `/docs` closure exists, broader knowledge-product experience still needs execution.
- `Data / logic quality`: good. Content model and lifecycle are explicit.
- `Integration quality`: good. The package already connects help, home, modules, and Teresa.
- `Trust / governance`: good. Editorial and SuperAdmin governance are explicit.
- `Market standard fit`: partial to good. Strong doctrine, incomplete runtime depth.

## 7. Main gaps

- content seeding and editorial operations are not yet fully realized,
- Teresa recommendation and contextual recommendation logic still need runtime closure,
- the broader knowledge product is stronger in docs than in live product breadth,
- carried Wave 1 closeout should not be mistaken for full module completion.

## 8. Minimal acceptance state now

The first acceptable Wave 2 state is:

- one canonical `/docs` plus authenticated help experience,
- contextual module help and Teresa help entry,
- governed content lifecycle,
- and enough seeded content that the module feels real, not skeletal.

## 9. Full 100% target state

`Help / Knowledge Base` reaches 100% only when it includes:

- serious help center depth,
- transformation knowledge depth,
- contextual recommendations across key surfaces,
- Teresa-guided discovery,
- editorial and recommendation operations,
- community/resource/update layers,
- and academy-adjacent enablement where the package says it belongs.

## 10. Top missing functions and flows

- contextual recommendation logic
- homepage/help/teresa knowledge surfacing
- editorial workflow operationalization
- seeded collections, articles, guides, and support resources
- consistent handoff between help, KB, and deeper enablement

## 11. Proposed bounded delivery packets

1. `Knowledge product runtime closure`
   - make the broader KB feel like a real module
2. `Contextual recommendation engine`
   - connect help recommendations to live module context
3. `Editorial and content ops`
   - close lifecycle, curation, and governance operations
4. `Seeded content and journeys`
   - ensure users encounter a meaningful knowledge product on day one

## 12. Risks and dependencies

- depends on `Teresa`, `Knowledge RAG`, and `Superadmin content ops`,
- risks becoming only a docs library,
- risks splitting into support help vs knowledge vs academy without one clear system.
