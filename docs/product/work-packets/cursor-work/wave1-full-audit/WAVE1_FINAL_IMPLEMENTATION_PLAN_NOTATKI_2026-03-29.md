## 3. Benchmark Family From `Softs`

Primary benchmark family:

- `Softs/0 Notatki`

Benchmark interpretation:

- durable working memory
- strong attachment and object linkage
- credible provenance and review semantics
- calm transition from capture to structured reuse

## 4. Intended Final Product Behavior

`Notatki` should behave like a trustworthy operating memory:

- capture is easy
- attachments and linked objects stay readable
- AI assistance improves, but does not blur provenance
- the user understands source quality, reviewer state, and output lineage
- notebook artifacts can move into other work lanes without losing trust

## 5. Current Repo Truth

What is already true:

- the core notebook lane is one of the strongest Wave 1 surfaces
- closure-grade honesty and core continuity are proven
- provenance readback and main-path governance are materially stronger

What is still incomplete:

- adjunct breadth for uploads and attachments is uneven
- object-linked propagation into other modules is not deep enough
- reviewer semantics and verified/disputed language are still lighter than ideal
- broader orchestration coverage remains partial

## 6. Gap Ledger

| Dimension | Current truth | Final implementation requirement | Main gap |
| --- | --- | --- | --- |
| `User value` | strong on core note path | strong across capture, attachment, and reuse breadth | adjunct breadth |
| `Flow completeness` | core capture and review work | notebook-to-other-module continuity must be stronger | handoff depth |
| `UX quality` | credible and useful | calmer provenance and review language across more cases | provenance clarity |
| `Data / logic quality` | strong core lane | stronger linked-output and attachment handling | object linkage breadth |
| `Integration quality` | medium | notebook must connect more cleanly into neighboring modules | cross-module propagation |
| `Trust / governance / error handling` | strong | preserve trust while expanding surface area | reviewer semantics |
| `Market standard fit` | medium-strong | closer to durable working-memory expectations | breadth vs depth gap |

## 7. Final Delivery Packets

| Packet | Goal | Scope | What we deliver | What we do not touch | Acceptance proof |
| --- | --- | --- | --- | --- | --- |
| `Notebook adjunct breadth packet` | make the module stronger beyond the core lane | attachments, uploads, object-linked context, adjunct readback | more complete attachment and linked-object treatment on declared notebook paths | broad document platform or output suite work | a user can attach, inspect, and reuse declared artifact types without losing trust in notebook state |
| `Notebook provenance and reviewer semantics packet` | improve trust language | verified/disputed semantics, source badges, reviewer language | clearer provenance labels and bounded reviewer status grammar | legal-signoff workflow or enterprise records system | the user can tell what was captured, transformed, reviewed, or disputed without reading implementation detail |
| `Notebook cross-module continuity packet` | strengthen notebook reuse in the product spine | handoffs into `Radar`, `Inicjatywy`, `Teresa`, and other declared consumers | context-preserving notebook links and more explicit downstream reuse states | redesign of downstream modules | notebook-originated context remains understandable after it leaves the notebook lane |

## 8. Dependencies And Risks

Dependencies:

- `Radar`
- `Teresa`
- `Inicjatywy`
- broader object and attachment services

Risks:

- growing attachment breadth without a coherent provenance model
- overstating AI-derived notebook outputs as verified truth
- expanding notebook scope into an unbounded document platform

## 9. Final Acceptance Bar

`Notatki` is finally implemented for its declared Wave 1 role only when:

- the main notebook journey remains strong
- attachments and linked objects are trustworthy on the declared lanes
- provenance and review language are explicit and consistent
- notebook context can move into downstream surfaces without ambiguity

## 10. Non-Goals And Unsafe Claims

Non-goals:

- building a full office-documents suite
- claiming universal attachment parity
- replacing downstream work modules with notebook logic

Unsafe claims until separately proven:

- `Notatki now delivers full Notion-class breadth`
- `all notebook-linked outputs are fully governed end to end`
- `every notebook artifact is equally reusable across the entire product`
