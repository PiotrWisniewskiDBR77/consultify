# Wave 2 Final Implementation Plan - Help / Baza wiedzy

Date: 2026-03-29
Module: `Help / Baza wiedzy`
Scope: final implementation plan for the user-facing Wave 2 support, knowledge, and contextual guidance product

## 1. Scope

This plan covers only `Help / Baza wiedzy` as the combined support-and-knowledge product.

It does not widen scope into:

- full standalone `Edukacja`
- broad partner enablement ownership
- pretending that bounded help closeout already equals full knowledge-product completion

## 3. Benchmark Family From `Softs`

Primary benchmark family:

- contextual help centers, knowledge products, and guided support systems

Benchmark interpretation:

- help should be easy to enter and trust
- knowledge should feel curated, not dumped
- contextual recommendation matters
- content ops and seeding are part of the product, not only editorial back office

## 4. Intended Final Product Behavior

`Help / Baza wiedzy` should behave like one support and knowledge product:

- one clear help entry
- contextual guidance from relevant surfaces
- curated transformation knowledge
- Teresa-led discovery into the right content and next step

## 5. Current Repo Truth

What is already true:

- documentation depth is strong
- bounded help closeout is real
- runtime surfaces for docs/help already exist

What is still incomplete:

- content seeding and editorial operations still need stronger product packaging
- contextual recommendation depth remains open
- the broad knowledge product is still more mature in docs than in lived runtime

## 6. Gap Ledger

| Dimension | Current truth | Final requirement | Main gap |
| --- | --- | --- | --- |
| `User value` | help baseline is real | full support-and-knowledge product | productization depth |
| `Flow completeness` | entry and browse basics exist | discover-learn-apply-next-step sequence | contextual guidance |
| `UX quality` | docs and KB surfaces exist | one calm and guided help product | shell cohesion |
| `Data / logic quality` | content and help logic exist | recommendations and curation must be explicit | recommendation depth |
| `Integration quality` | Teresa and product surfaces can connect | contextual support should behave consistently | contextual continuity |
| `Trust / governance / error handling` | bounded honesty is good | editorial and content governance must stay visible | content ops clarity |
| `Market standard fit` | medium | serious support and transformation KB | runtime depth |

## 7. Final Delivery Packets

| Packet | Goal | Scope | What we deliver | What we do not touch | Acceptance proof |
| --- | --- | --- | --- | --- | --- |
| `Knowledge product runtime packet` | make KB feel like a real module | entry shell, help routing, primary KB experience | one explicit support and knowledge module | full academy runtime | users can enter and use one believable help product |
| `Contextual recommendation packet` | tie knowledge to work | module-context help, Teresa guidance, recommendation logic | stronger in-product guidance | every AI recommendation in the platform | users receive context-aware help that matches their current surface |
| `Editorial and content ops packet` | make the knowledge layer durable | curation, lifecycle, seed quality, operational ownership | more believable content maturity | full community platform | the knowledge product no longer feels like a thin shell over sparse content |

## 8. Dependencies And Risks

Dependencies:

- `Teresa`
- Knowledge retrieval layers
- `Superadmin` content operations
- `Edukacja` as adjacent but separate scope

Risks:

- collapsing knowledge product scope back into generic docs
- assuming strong documentation equals strong runtime product
- letting `Edukacja` disappear inside Help

## 9. Final Acceptance Bar

`Help / Baza wiedzy` is finally implemented for its declared Wave 2 role only when:

- it behaves like one support and knowledge product
- contextual recommendations are visible on key declared surfaces
- content depth and editorial ownership are believable
- bounded help closeout is clearly separated from broader knowledge-product completeness

## 10. Non-Goals And Unsafe Claims

Non-goals:

- full academy scope
- full community platform
- claiming that a strong docs portal alone completes the module

Unsafe claims until separately proven:

- `the transformation knowledge product is fully complete`
- `all recommendation logic is solved`
- `Help now covers standalone education by itself`
