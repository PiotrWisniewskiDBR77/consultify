## 1. Why this document exists

Managing virtual workers is not the same as editing one prompt.

Leader systems treat worker operations as a control plane with:

- registry and identity
- profile and policy versioning
- governed knowledge
- channel controls
- evals and release management
- conversation intelligence
- auditability

This benchmark defines what `consultify` should learn and adapt for `Virtual Workers`, with `Anna` as the primary first-class worker.

Rule:

`consultify` should adapt operator patterns, not copy competitor UI`

## 3. What the leaders teach

### 3.1 Registry-first worker operations

Leaders do not treat assistants as hidden prompt files.

They expose:

- explicit worker identity
- clear owner
- environment/surface scope
- active/draft/disabled state
- version lineage

Imported lesson:

`a worker must be operated as a product surface, not as an invisible backend configuration`

### 3.2 Knowledge as governed assets

Leaders do not treat knowledge as one undifferentiated blob.

They expose:

- source objects
- sections or scopes
- assignment controls
- freshness / status
- preview of injected context

Imported lesson:

`operator trust increases when knowledge can be inspected, limited, weighted and released deliberately`

### 3.3 Memory as policy, not magic

The strongest systems separate:

- session memory
- working memory
- durable memory
- forbidden memory

Imported lesson:

`memory must be explicit, bounded and operator-readable`

### 3.4 Conversation intelligence beyond transcripts

Leader operator tools summarize:

- topic
- intent
- resolution state
- escalation reason
- knowledge gap
- conversation length
- quality drift

Imported lesson:

`operators need structured conversation intelligence, not only raw transcripts`

### 3.5 Channel parity

Modern assistant systems do not accept one worker behaving like two different products across text and voice.

Imported lesson:

`channels may differ in transport, but they should share one worker doctrine, one policy model and one runtime memory truth`

### 3.6 Evals and release discipline

Prompt/profile changes should not go live as unreviewed edits.

Leaders use:

- test suites
- benchmark datasets
- regression comparisons
- staged rollout
- rollback

Imported lesson:

`worker quality must be release-managed, not only edited`

## 4. Benchmark patterns `consultify` should adopt

### 4.1 Worker cockpit, not only tabs

`Superadmin -> Virtual Workers` should feel like an operator cockpit where one can:

- configure the worker
- inspect knowledge
- review conversations
- understand topics and failures
- run evaluations
- release safely

### 4.2 Knowledge pills as first-class governed objects

`consultify` should introduce full `knowledge pills` with:

- product identity
- buyer fit
- capabilities
- limitations
- objection handling
- CTA guidance
- evidence links
- language variants
- editorial status

### 4.3 Structured topic intelligence

Operators should see:

- primary topic
- subtopics
- discussed products
- user intent
- outcome
- fallback reason
- knowledge gaps

### 4.4 Privacy-first analytics

Benchmark target is not unlimited transcript storage.

Benchmark target is:

- transcript-light analytics
- structured summaries
- durable aggregate insight
- limited sensitive retention

### 4.5 Anna as package benchmark

The first worker should not be a toy.

`Anna` should become the benchmark worker that proves:

- public worker governance
- product knowledge control
- topic analytics
- voice/text parity
- operator-driven continuous improvement

## 6. 100% target state

`Virtual Workers` reaches leader-grade quality when it includes:

- one canonical worker registry
- profile versioning with release history

- memory policy controls

- eval suite and regression gates
- rollout / rollback controls
- full audit trail for operator changes
