# MAT-002-T01 — brief, typed variables i lineage przy tworzeniu prezentacji z wzorca

Status: `READY_SERIAL_INTEGRATOR / PREFLIGHT_REQUIRED`

Baseline przygotowania: `88db01dc0`

Gap: `MAT-002-G01`

Owner danych: Presentations

Jedyny writer: `POST /api/presentations/decks/from-template`

## Objective

Zatrzymać automatyczną materializację prezentacji natychmiast po wejściu z
`templateArtifactId`. Najpierw pokazać dostępny brief, tytuł, pochodzenie wzorca
i kontrolki zmiennych z kanonicznego katalogu. Deck można utworzyć dopiero po
wypełnieniu briefu i wszystkich wymaganych wartości; backend ponownie rozwiązuje
wzorzec, waliduje wartości i zapisuje lineage wraz z faktami użytymi do slajdów.

## AS-IS

- `PrezentacjeView.tsx` w efekcie linii około 454–483 wysyła tylko
  `{ templateArtifactId }` i natychmiast nawiguje do Deck Buildera.
- `/templates/resolve` nie zwraca `variables`; `/decks/from-template` akceptuje
  tylko `templateArtifactId` i opcjonalny `title`.
- Resolver `materials/creationIntent.ts` już zwraca świeży `customTemplate`.
- `presentationTemplateRuntimeService.ts` już ma walidator typed variables,
  `materializeTemplateVariableBrief` oraz `mapOutlineBlueprintToDeckSlides(…, brief)`.
  Route nie używa tych gotowych funkcji przy materializacji.
- Test `PrezentacjeView.templateBrief.test.tsx` jest wymaganiem produktu, nie
  historycznym harness-em.

## TO-BE

`/templates/resolve` zwraca publiczny, sanitizowany kontrakt variables. UI buduje
kontrolki `text|number|date|boolean|enum`, pokazuje required/default/description,
brief i tytuł. Backend ponownie rozwiązuje wzorzec i sam waliduje wartości; nie
ufa wcześniejszemu resolve. Brief oraz zmaterializowane linie zmiennych zasilają
deterministyczne slajdy, a `source_refs_json` zapisuje template artifact,
canonical template, brief/facts hash i użyte klucze zmiennych bez sekretów.

## Request/response contract

Resolve response dodaje:

```ts
variables: Array<{
  key: string;
  label: string;
  type: 'text' | 'number' | 'date' | 'boolean' | 'enum';
  required: boolean;
  defaultValue?: string | number | boolean;
  description?: string;
  options?: string[];
}>;
```

Create body:

```ts
{
  templateArtifactId: string;
  title?: string;
  brief: string;
  variableValues: Record<string, string | number | boolean>;
}
```

Backend odrzuca: pusty brief, brak required, nieznany key, zły typ, enum spoza
options, forbidden/orphaned/deprecated template oraz obcy tenant. Error codes są
stabilne i mapowane na komunikat UI; brak fallbacku do pustego decka lub AI.

## Required cases

- zero variables + brief;
- number i enum required; default value; boolean false nie jest traktowane jako brak;
- missing/unknown/wrong type/bad enum;
- resolver zmieniony pomiędzy resolve i create;
- tenant denial oraz template lifecycle denial;
- retry/idempotency nie tworzy dwóch decków (jeżeli endpoint nie ma dziś
  idempotency key, task musi dodać go przed `READY`, a nie pominąć test);
- zapisane cards zawierają brief facts, lineage ma canonical template i hash;
- cold reopen oraz PPTX export zachowują title, facts i template visual identity.
