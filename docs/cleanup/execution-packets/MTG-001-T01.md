## Objective

Rozszerzyć aktywny, prosty moduł Meeting o jeden trwały lifecycle spotkania,
role spotkania, notatki oraz proposal-first materializację decyzji i zadań.
Spotkanie może zostać zamknięte tylko uczciwie: API raportuje każdy output
PROPOSED, APPROVED, MATERIALIZING lub FAILED, potrafi pojednać przerwany zapis i
nigdy nie odpowiada 200 dla przegranego wyścigu lub nieistniejącego rezultatu.

Nie zastępować aktywnego CRUD ani `MeetingHub` odzyskanym branchem. Portować
kontrakt domenowy commit po commicie na aktualny route/service i aktualne modele
Task/Decision.

## AS-IS

- `/meeting` montuje `MeetingHub`; `/api/meeting` ma CRUD, agenda,
  uczestników, pre-read, follow-ups i AI notes.
- `meetingService.ts` posiada tylko status `scheduled|completed`; nie ma
  proposal-first minutes/output lifecycle.
- Aktualny realDB M12 gate dowodzi podstawowego CRUD, ale nie dowodzi
  `proposed summary -> approve -> one decision + task + material`.
- W kanonie nie ma migracji `20260801_meeting_core.sql`, katalogu
  `server/src/services/meetingCore/` ani tabel participants/notes/outputs.
- Odzyskany trzycommitowy kandydat zawiera lifecycle, role, notatki, outputy,
  transakcje, testy współbieżności i reconciliation. Nie jest przodkiem kanonu i
  nie wolno scalać go jako całej gałęzi.
- Odzyskany finding pozostawia otwartą idempotencję `proposeOutput`; pakiet nie
  może zostać uznany za READY bez jej domknięcia.

## TO-BE

Jeden Meeting ID obsługuje przygotowanie, LIVE, CLOSING i CLOSED. Teresa lub
człowiek dodaje notatkę i może zaproponować task/decision, ale żadna propozycja
nie mutuje modułu docelowego przed zatwierdzeniem uprawnionego człowieka.
Zatwierdzony output materializuje dokładnie jeden obiekt docelowy z
`sourceType=meeting`, `sourceId=meetingId/outputId` i idempotency key.
Przerwany proces w `MATERIALIZING` jest pojednany przez readback obiektu
docelowego. Przegrany CAS zwraca 409. Cold reopen pokazuje zatwierdzone minutes,
pełny audit i wszystkie rezultaty.

## API contract

Minimalne operacje:

- create/get aggregate;
- participants add/remove/list;
- notes add/archive/list;
- lifecycle transition i close;
- outputs propose/approve/reject/materialize/reconcile.

Każda mutacja wymaga tenant identity z tokenu, meeting role/capability,
`expectedVersion` lub równoważnego CAS oraz `Idempotency-Key` tam, gdzie może
powstać trwały obiekt. Teresa nie approve/reject/reconcile.

## Required cases

- create -> prepare -> live -> note -> proposed summary;
- proposal nie tworzy task/decision;
- approve + materialize tworzy dokładnie jeden task i jedną decyzję;
- retry i dwa równoległe żądania nie tworzą duplikatów;
- ten sam idempotency key z innym payloadem -> 409;
- MATERIALIZING + obiekt istnieje -> reconcile MATERIALIZED z tym samym ID;
- MATERIALIZING + brak obiektu -> MATERIALIZATION_FAILED i bezpieczny retry;
- close raportuje rozłącznie PROPOSED+APPROVED, MATERIALIZING i FAILED;
- przegrany lifecycle/output CAS -> 409, nigdy 500;
- cross-org -> 404 bez potwierdzenia istnienia;
- participant/observer/teresa forbidden cases;
- cold reopen, audit ordering i source lineage;
- consent oraz retention state nie mogą być domyślnie uznane za zaakceptowane.
