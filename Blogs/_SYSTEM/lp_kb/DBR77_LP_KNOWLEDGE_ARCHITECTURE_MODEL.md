# DBR77 LP Knowledge Architecture Model

## Purpose

This document defines how every DBR77 product landing page should work as the front door to a mature knowledge system.

It exists to prevent three failure modes:

- thin sales page plus a blog link
- chronological article list with no logic
- fragmented product narratives that break the DBR77 system story

## Core Rule

Each product LP is an independent entry gate.

The buyer should enter through a specific problem first.

The wider DBR77 system should appear progressively through proof, related sections, and cross-product bridges.

## What Every Product LP Must Do

Each LP must:

1. explain the product value proposition clearly
2. prove the real industrial problem in buyer language
3. offer decision or use-case paths
4. organize knowledge into grouped sections, not date-based lists
5. show proof and implementation depth
6. present CTA paths matched to buyer maturity

## Shared LP Structure

Use this sequence as the default model for all product landing pages.

### 1. Hero Value Proposition

Goal:

- explain what the product is
- make the primary problem obvious
- show the first safe next step

Must include:

- one-sentence product promise
- one primary persona bridge
- one maturity-matched CTA

### 2. Problem Reality Block

Goal:

- prove the problem is real
- show repeated field reality
- make the buyer feel understood

Must include:

- operational specificity
- common failure pattern
- role-specific consequence

### 3. Decision Or Use-Case Paths

Goal:

- help the buyer choose where to start
- reduce cognitive load
- route different maturity levels to the right section

Typical path labels:

- understand the problem
- compare options
- see implementation path
- review proof
- start a demo, trial, pilot, or decision call

### 4. Grouped Knowledge Sections

Goal:

- turn the LP into a knowledge system, not a static sales page
- make depth visible fast
- organize article libraries by decision logic

Each grouped section should contain:

- section promise
- short buyer-intent intro
- curated article cluster
- optional proof block
- section-level CTA

### 5. Proof And Implementation Block

Goal:

- show the company knows how work moves after the decision
- connect idea to execution

Possible components:

- proof snapshots
- case-shaped observations
- implementation warnings
- rollout or adoption content

### 6. CTA Ladder

Goal:

- give the buyer the right next step for current maturity
- avoid one-CTA-fits-all behavior

Use three CTA depths where possible:

- low commitment: read, benchmark, explore
- medium commitment: demo, trial, pilot, workshop
- high commitment: validate fit, review security, discuss business case, schedule decision meeting

## Recommended Public Section Labels

Use these shared labels across the DBR77 system where they fit the product:

- `Downtime And OEE`
- `Layout And Flow`
- `CAPEX And Investment`
- `Governance And ROI`
- `Automation And Sourcing`
- `AI And Decision Making`
- `Execution And Rollout`

Not every product should use every label.

The model should reuse labels where they genuinely fit, so the system feels coherent without becoming generic.

## Knowledge Section Template

Every grouped knowledge section should follow this internal pattern:

1. section label
2. one-sentence buyer problem
3. `3-6` featured articles
4. one proof or implementation block
5. one stage-matched CTA

Do not dump all `50` articles on the LP at once.

The LP should surface the best cluster first and allow deeper exploration from there.

## Article-To-Section Rule

Each article should have:

- one primary LP section
- optional secondary cross-link

This keeps:

- internal linking cleaner
- LP curation easier
- cross-product bridges intentional

## Proof Block Model

Each LP should include at least two proof-bearing blocks.

Use blocks such as:

- reality-check pattern
- decision mistakes buyers usually make
- implementation warning block
- case-shaped observation
- outcome logic summary

Do not rely on adjectives alone.

## Face And Persona Integration Rule

Faces and personas should guide routing, not dominate page structure.

LPs should show:

- the right expert where trust needs strengthening
- the right product logic first
- the right CTA path by maturity

LPs should not become:

- face galleries
- personal-brand pages
- social-profile mirrors

## Cross-Product Bridge Rule

Cross-product bridges should appear only after the primary product problem is clear.

Use bridges like:

- `IoT` -> `IRIS` when visibility becomes execution
- `DT` -> `Marketplace` when simulation supports automation buying
- `Consultify` -> `DT` or `IRIS` when strategy becomes operating change
- `Vector` -> `IRIS` when secure AI moves into governed execution

Bridge placement should be later on the page than the primary product explanation.

### Early maturity

Use:

- read

### Mid maturity

Use:

- start demo
- start trial
- plan pilot
- book workshop

### Late maturity

Use:

- validate fit
- review business case
- review security
- schedule decision meeting

## LP Quality Test

A landing page is structurally correct when:

- a new buyer can tell which problem this product solves
- a serious buyer can see grouped knowledge depth quickly
- the page offers more than one maturity path
- the proof feels like accumulated industrial practice
- the broader DBR77 system appears without confusing the first step

## What Not To Do

Do not use:

- generic date-sorted blog feeds as the main LP knowledge area
- random article cards with no section logic
- single CTA pressure with no maturity ladder
- product pages that hide proof below long abstract copy
- cross-product bridges before the primary problem is clear
