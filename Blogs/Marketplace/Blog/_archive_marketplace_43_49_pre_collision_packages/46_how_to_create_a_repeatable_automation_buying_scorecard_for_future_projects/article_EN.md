# How to Create a Repeatable Automation Buying Scorecard for Future Projects

Target persona: Technical and commercial buyer team  
Funnel stage: Evaluation (scoring suppliers with comparability)  
Core problem: scorecards drift per project, so teams cannot defend award logic or improve over time  
Main promise: a stable scorecard skeleton with explicit weights, evidence rules, and calibration discipline

A scorecard is not a vibe check with numbers.

It is a comparability machine.

If the dimensions change every time you are tired, you cannot explain the award.

If the evidence rules are soft, integrators learn to optimize slides, not delivery risk.

## Direct answer

Create a repeatable automation buying scorecard by fixing a small set of dimensions (typically eight to twelve), assigning weights that sum to one hundred percent, defining objective evidence per dimension, requiring the same artifact types from each bidder, running a calibration session before scoring, and archiving the scored matrix with rationale notes tied to acceptance and schedule risk.

Repeatability means the next project changes weights or dimensions only through a written rationale, not through hallway preference.

## Scorecard skeleton (example structure, not universal)

| Dimension group | example dimensions |
| --- | --- |
| scope fit | process coverage, exception handling, layout fit |
| technical proof | reference similarity, test evidence, software maturity |
| delivery | plan credibility, dependency handling, resource stability |
| commercial | TCO transparency, milestone alignment, remedy clarity |
| risk and governance | safety approach, change discipline, documentation quality |
| partnership | escalation model, training plan, spare parts realism |

Your plant may merge or split groups.

The rule is: every dimension must map to something you can verify without heroics.

## Evidence rules (non-negotiable)

For each dimension, publish:

- what counts as proof (document type, test type, site visit outcome)
- what counts as insufficient (narrative only, unnamed references)
- who verifies on the buyer side

If two bidders cannot be scored on the same basis, the dimension is broken.

## Calibration protocol (ninety minutes, illustrative)

1. read two anonymized excerpts from past projects where scoring went wrong  
2. score a dummy bid as a group and disagree on purpose  
3. lock tie-break rules: safety first, then acceptance evidence, then schedule credibility  

Publish calibration notes with the scorecard version ID.

## Checklist before you call the scorecard "repeatable"

- weights sum to one hundred and are approved by named roles  
- each dimension has verifier and minimum evidence  
- scoring happens on one controlled template, not scattered spreadsheets  
- post-award review compares predicted risks to what actually happened  

## What this means for DBR77 Marketplace

DBR77 Marketplace is a workflow for automation decisions, a trust layer for integrator selection, and a system for comparing offers and reducing sourcing chaos.

A repeatable scorecard is the buyer-side mirror of structured offer comparison.

Marketplace is not a robot catalog.

It is manufacturer-first infrastructure for defensible award logic.

## Bottom line

If you cannot reconstruct why the winner won six months later, you did not have a scorecard.

You had a story with decimals.
