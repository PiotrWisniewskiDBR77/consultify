## 1. Root cause found

**Symptom** (documented pre-existing incident): `docs/program/WEEKEND_COMPLETION_2026-08-01/PACKETS/MAT-006B_PRESENTATION_LIFECYCLE_E2E.md` — on `demo.consultify.ai`, deck `atelier--deck--line3-steering` showed `Ready`, `11` slides in the Materials list, but opening the builder showed `Card 1 of 0` and the toast "Deck has no content yet. Generate slides first."

**Cause, confirmed by code + live repro**: two creation routes in `server/src/routes/presentations.routes.ts` —
- `POST /decks` (line ~1672, "create a deck directly from structured slide JSON — used by Table OS export")
- `POST /decks/from-template` (line ~1798)

both wrote an accurate `slide_count` onto `presentation_decks`, but persisted the actual slide content **only** into `presentation_cards` — a table `normalizeDeckDocument()` (the single canonical reader in `server/src/services/presentationDeckDocumentService.ts`, called by every `GET /decks/:id`) **never reads**, and which is not even reliably present in every environment (see §5, gap 2). `deck_json`/`unified_json` were left `NULL`. `DeckBuilder.tsx`'s load effect (`src/components/Presentations/DeckBuilder/DeckBuilder.tsx:615-744`) checks `Array.isArray(deckJson.cards)`, finds nothing, falls through to its empty-shell branch, and shows exactly the toast from the incident.

The AI-generation write path (`presentationGeneratorService.ts:2127`, the only other place that sets `status='ready'`) was already internally consistent — it always writes `deck_json` and `slide_count` together in one `UPDATE`. So the bug is scoped to the two "structured/template" creation routes, not the generator.

**Live before/after repro** (local, see §3): created an 11-slide deck via `POST /decks` against the **unmodified** code (`git stash` of my fix) — result: `slide_count: 11`, `deck_json: null`, 11 orphaned rows in `presentation_cards`. Same request against the **fixed** code — result: `deck_json.cards.length === 11 === slide_count`.

## 2. What changed

- **`server/src/services/presentationDeckDocumentService.ts`** — new exported `buildDeckDocumentFromStructuredSlides()` (+ helper `structuredSlideToCard`). Turns the loosely-typed `{ type, content }` slide payloads these two routes accept into a proper `schemaVersion: 1` `DeckDocument` with real `DeckDocumentCard[]` (heading/paragraph/bullet_list blocks derived from `content.title/subtitle/body/items/messages`, or the pre-flattened `content.blocks` shape `mapOutlineBlueprintToDeckSlides` produces for the template route). - **Tests**: `server/src/services/__tests__/presentationDeckDocumentService.buildDeckDocumentFromStructuredSlides.test.ts` — 4 targeted tests (11-slide repro shape, round-trip through the exact `normalizeDeckDocument` function `GET /decks/:id` calls, the from-template nested-blocks shape, never-empty-for-non-empty-input). ## 5. Known gaps / NOT done

### 8.1 Fixed: workstreams.routes.ts blanket auth was intercepting the public share route (was §5.3)

**Confirmed root cause**, not just suspected: `app.use('/api', workstreamsRoutes)` (`Gateway.ts:984`) runs before `app.use('/api/presentations', ...)` (`Gateway.ts:1025`). `workstreams.routes.ts:77` had `router.use(verifyToken)` with **no path scope**, which in Express intercepts *every* request under `/api/*` that reaches that middleware layer — including `GET /api/presentations/shared/:token`, which `Gateway.ts` deliberately carves out of the beta gate (`createBetaGate(['/shared/', '/embed/'])`) specifically so it's public.

This exact bug class was already found and fixed once before in this codebase — `server/src/routes/transactionReadiness.routes.ts` carries a 2026-07-20 comment describing the identical failure mode and fix. `workstreams.routes.ts` just hadn't received the same fix.

**Fix applied** (`server/src/routes/pmo/workstreams.routes.ts`): scoped the guard to this router's own two path families instead of a blanket `.use()`:
```ts
router.use('/projects/:projectId/workstreams', verifyToken);
router.use('/workstreams', verifyToken);
```
No other line in the file changed — same two path families the router itself already serves (`/projects/:projectId/workstreams`, `/workstreams/:workstreamId/*`).

**Proof, through the real mount order** (`server/scripts/mat007-gateway-order-proof.ts`, new — mounts `workstreamsRoutes` then `presentationsRoutes` in the exact Gateway.ts order and paths, not a substitute):
- Before the fix (confirmed via `git stash` of just this one change): `GET /api/presentations/shared/nonexistent-token` (no auth header) → **401** `{"error":"No token provided"}` — the bug reproduces exactly as diagnosed.
- After the fix: same request → **404** `{"success":false,"error":"Shared presentation not found"}` — request now reaches `presentations.routes.ts`'s own logic, which correctly 404s an unknown token instead of being blocked upstream.
- Regression check both before and after: `GET /api/projects/:id/workstreams` and `GET /api/workstreams/:id` (unauthenticated) → **401** in both cases — workstreams' own auth protection is unchanged, only its blast radius on unrelated routes is fixed.
- Full real lifecycle through this same correctly-ordered mount (real Postgres, real create → share → revoke, cleaned up after): `POST /decks` (11 slides) → 201 → `GET /decks/:id` → 11 cards (root-cause fix confirmed working here too) → `POST /decks/:id/share` → 200 → **`GET /shared/:token` unauthenticated → 200 with real content** → `DELETE /decks/:id/share` → 200 → **`GET /shared/:token` again → 404**. This is the MAT-009 share/revoke requirement proven against the actual production route order, not a workaround.

The `server/scripts/mat007-isolated-share-check.ts` harness from the first pass is now superseded by this — kept in the repo as-is since it's harmless test tooling, but `mat007-gateway-order-proof.ts` is the one that actually proves the requirement.

### 9.1 Fresh-from-zero migration via the sanctioned runner — additive fix, not a global schema repair

```
✗ 20260623_distribution_delivery.sql: relation "status_reports" does not exist
```
Root cause (confirmed by reading the file, not guessed): `20260623_distribution_delivery.sql` already carries a documented "FRESH-DB GUARD" for `report_distributions` (`CREATE TABLE IF NOT EXISTS ... -- originally created by 066_status_reports.sql, which the Postgres runner filters out (<500 legacy)`), but its `FOREIGN KEY (report_id) REFERENCES status_reports(id)` still points at `status_reports` — the table that exact same comment names as filtered-out — which nobody ever re-guarded. This is a **pre-existing, repo-wide, unrelated-to-presentations migration-ordering gap** (status reports / distribution feature, nothing to do with MAT-007/009). Per instruction, this is reported and **not fixed** — fixing it would mean either renumbering/exempting `066_status_reports.sql` from the legacy filter (a repo-wide policy change) or re-guarding `status_reports` itself in that unrelated file, neither of which is "the smallest additive migration for MAT-007/009."

**With `--safe`** (a built-in, documented flag of the same sanctioned runner — not a manual DB edit): 290 of 317 migrations apply; 27 skip, all for entirely unrelated subsystems (initiatives, GDPR, admin sessions, MCP providers, inbox, invoices, KPI snapshots, agent folders, etc. — none touch presentations). Full skip list is in the run log; none are new findings beyond the two `20260719_*` gaps already reported in §8.3/§5.2.

After that run, `presentation_cards` and `audit_events` were confirmed still missing — because both are declared **only** inside `20260719_baseline_gap.sql`, which fails on an unrelated `ai_feedback` statement and rolls back as one transaction (§5.2), losing every table it declares including these two.
