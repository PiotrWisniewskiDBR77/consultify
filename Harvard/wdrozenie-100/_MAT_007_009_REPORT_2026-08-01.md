## 1. Root cause found

**Symptom** (documented pre-existing incident): `docs/program/WEEKEND_COMPLETION_2026-08-01/PACKETS/MAT-006B_PRESENTATION_LIFECYCLE_E2E.md` — on `demo.consultify.ai`, deck `atelier--deck--line3-steering` showed `Ready`, `11` slides in the Materials list, but opening the builder showed `Card 1 of 0` and the toast "Deck has no content yet. Generate slides first."

**Cause, confirmed by code + live repro**: two creation routes in `server/src/routes/presentations.routes.ts` —
- `POST /decks` (line ~1672, "create a deck directly from structured slide JSON — used by Table OS export")
- `POST /decks/from-template` (line ~1798)

both wrote an accurate `slide_count` onto `presentation_decks`, but persisted the actual slide content **only** into `presentation_cards` — a table `normalizeDeckDocument()` (the single canonical reader in `server/src/services/presentationDeckDocumentService.ts`, called by every `GET /decks/:id`) **never reads**, and which is not even reliably present in every environment (see §5, gap 2). `deck_json`/`unified_json` were left `NULL`. `DeckBuilder.tsx`'s load effect (`src/components/Presentations/DeckBuilder/DeckBuilder.tsx:615-744`) checks `Array.isArray(deckJson.cards)`, finds nothing, falls through to its empty-shell branch, and shows exactly the toast from the incident.

The AI-generation write path (`presentationGeneratorService.ts:2127`, the only other place that sets `status='ready'`) was already internally consistent — it always writes `deck_json` and `slide_count` together in one `UPDATE`. So the bug is scoped to the two "structured/template" creation routes, not the generator.

**Live before/after repro** (local, see §3): created an 11-slide deck via `POST /decks` against the **unmodified** code (`git stash` of my fix) — result: `slide_count: 11`, `deck_json: null`, 11 orphaned rows in `presentation_cards`. Same request against the **fixed** code — result: `deck_json.cards.length === 11 === slide_count`.

## 2. What changed

- **`server/src/services/presentationDeckDocumentService.ts`** — new exported `buildDeckDocumentFromStructuredSlides()` (+ helper `structuredSlideToCard`). Turns the loosely-typed `{ type, content }` slide payloads these two routes accept into a proper `schemaVersion: 1` `DeckDocument` with real `DeckDocumentCard[]` (heading/paragraph/bullet_list blocks derived from `content.title/subtitle/body/items/messages`, or the pre-flattened `content.blocks` shape `mapOutlineBlueprintToDeckSlides` produces for the template route). Falls back to dumping any remaining string fields as a paragraph so a slide never silently loses its only content.
- **`server/src/routes/presentations.routes.ts`** — both routes now call this builder and persist the result as `deck_json` in the same `INSERT` that sets `slide_count`, so the row is self-consistent from creation. The legacy `presentation_cards` insert is kept as a best-effort, non-fatal mirror (wrapped in try/catch — it must not block deck creation if the table is absent, see §5 gap 2).
- **Tests**: `server/src/services/__tests__/presentationDeckDocumentService.buildDeckDocumentFromStructuredSlides.test.ts` — 4 targeted tests (11-slide repro shape, round-trip through the exact `normalizeDeckDocument` function `GET /decks/:id` calls, the from-template nested-blocks shape, never-empty-for-non-empty-input). All pass; existing `presentationDeckDocumentService.*.test.ts` files (6 tests) still pass — no regression.
- **Not touched**: restore/history logic (MAT-08, frozen), any export renderer, share/revoke logic, Documents/Workbook modules, no new export formats.

## 4. Golden-flow steps proved (exact sequence)

1. Create (`POST /decks`, 11 slides, mirrors the MAT-006B incident) → `201`, `slideCount: 11`.
2. Open/reopen (`GET /decks/:id`, same call `DeckBuilder.tsx` makes) → `deck_json.cards.length === slide_count === 11` (was `null`/0 before the fix — proven via a live before/after `git stash` repro, see §1).
3. Edit a card client-side.
4. Autosave (`PUT /decks/:id/autosave`, CAS via `X-Deck-Version`) → version bump.
5. Read-back proof: independent `GET /decks/:id` shows the edit persisted server-side.
6. History (`GET /decks/:id/versions`) → pre-edit snapshot present.
7. Restore (`POST /decks/:id/versions/:versionId/restore`) → same deck ID, content reverted, version advanced (frozen MAT-08 mechanism, untouched).
8. Export PPTX (`GET /decks/:id/download`) → 200, valid OOXML file reflecting the current saved content.
9. Export PDF (`GET /decks/:id/export/pdf`) → 200, valid PDF, page count matches card count.
10. Share (`POST /decks/:id/share`) → token minted.
11. Public read (`GET /shared/:token`, no auth) → 200, real content, tenant fields stripped.
12. Revoke (`DELETE /decks/:id/share`) → 200.
13. Public read after revoke → **404** (verified as a real HTTP response, not a client-side flag).

## 5. Known gaps / NOT done

1. **Quality-gate override (`?overrideQualityGate=true`) is effectively dead for normal ADMIN/OWNER/SUPERADMIN users.** `server/src/routes/presentationExportGate.ts::canOverrideQualityGate` reads `req.user?.role || req.userRole`. `req.user.role` is always the **human-friendly, mapped** role string set by `mapRoleForAuthenticatedUser()` in `auth.middleware.ts` (e.g. DB role `ADMIN` → `req.user.role = 'administrator'`, `SUPERADMIN`/`OWNER` → `'owner'`) — it is **never** one of the raw codes (`'ADMIN' | 'OWNER' | 'SUPERADMIN'`) the override check compares against, and since it's truthy it always wins over `req.userRole` (which *does* hold the raw code) in the `||`. I found this empirically while testing export against a deck with zero traceability. **Not fixed** — unrelated to MAT-007/009, real product/security-relevant code (`presentationExportGate.ts`), worth its own ticket. Worked around it for the golden-flow proof by making the test deck carry real `source_refs` instead of relying on the override, which is also the more representative real-world path.
2. **`presentation_cards` (the legacy mirror table) is not reliably present.** On a fresh migration run (`server/scripts/migrate.postgres.ts --safe`), the migration file that defines it (`server/migrations/20260719_baseline_gap.sql`) fails on an earlier, unrelated statement (`relation "public.ai_feedback" does not exist`) and the whole file's transaction rolls back — so `presentation_cards`, `audit_events`, and others never get created on a from-scratch DB. This is a **pre-existing migration-ordering issue**, unrelated to my fix; I created the two missing tables directly in my local throwaway Postgres to unblock testing (not applied anywhere real). Confirms the legacy `presentation_cards` write path was already fragile/orphaned before this fix, independent of the empty-builder bug.
3. **Found, NOT fixed, spawned as a separate task**: `server/src/routes/pmo/workstreams.routes.ts:77` does `router.use(verifyToken)` with no path scope, and is mounted at bare `/api` (`Gateway.ts` ~line 984) — earlier in registration order than the presentations router (~line 1025). Because Express dispatches in registration order, this blanket guard intercepts **every** `/api/*` request that reaches that point, including the intentionally-public `GET /api/presentations/shared/:token` viewer, before it can ever reach `presentations.routes.ts`'s own (correctly, later-scoped) auth boundary. Confirmed via `req.baseUrl === '/api'` logged at the point of rejection. Production always runs the full Gateway (`server/src/index.ts` only skips it in test mode without `ENABLE_TEST_GATEWAY=true`), so **this may currently be breaking the real public share-link viewer on demo/production** — I could not verify against demo directly (out of scope / no Railway access from this task). Filed as a spawned follow-up task (`task_7607abf3`, title "Fix workstreams.routes.ts blanket auth blocking public /api routes") with full repro steps; **did not touch this file** — fixing Gateway-wide route ordering is outside MAT-007/009's scope and higher risk than warranted here. My golden-flow proof of steps 11-13 (public read / revoke / 404) used an isolated harness (`server/scripts/mat007-isolated-share-check.ts`) that mounts only the unmodified `presentations.routes.ts`, to verify that router's own contract is correct independent of this unrelated ordering bug.
4. **Decks created via `POST /decks`/`POST /decks/from-template` have no PPTX render triggered at creation time** — `export_path` is only ever set by the AI `generateDeck()` pipeline (`presentationGeneratorService.ts:2127`); the structured-slide routes never call the PPTX pipeline. This is a **separate, pre-existing gap** in those two routes (not something my fix introduces or was asked to close — "do not invent new export formats" / no generator changes) — a freshly-created structured deck's first `GET /decks/:id/download` will 404 with "Export not available" until something renders it once. For the golden-flow proof, I seeded the initial `export_path` using a test-only script (`server/scripts/mat007-seed-initial-export.ts`) that reuses the exact existing `PptxPipelineService` + `deckDocumentToUnifiedJson` — the same render call `generateDeck()` makes — so the subsequent `GET /decks/:id/download` calls in my proof exercise the real, unmodified download route (including its freshness re-render logic) rather than a stub.
